Diagnóstico rápido (situação hoje)
#	Sua pergunta	Situação real no projeto
1
Multi-usuário?
Parcial. Existe arquitetura (usuários, tenants, JWT, UserCompany), mas o piloto local usa SQLite + bypass de dev. Vários usuários simultâneos exigem PostgreSQL + login real + desligar bypass.
2
Trilingue?
Não. Interface e IA estão só em português. Não há i18n no frontend.
3
Dados salvos após upload?
Sim, grava no banco (FinancialStatement, ERPImportBatch, etc.), mas falta: camada clara de “depósito”, versionamento, purge seguro e garantia de que Templates não sobrescrevem tudo silenciosamente.
4
Treinar IA Operacional?
Não é fine-tuning hoje. É prompt + ferramentas (tools) que consultam dados reais. “Treinar” = ampliar tools, FAQ, exemplos e regras — não retreinar o modelo.
5
Base por dia/mês/ano?
Parcial. Há histórico de uploads e snapshots de ontologia; não há backup automático diário/mensal/anual do tenant.
6
Volume máximo?
Depende da infra. Piloto local (SQLite): centenas de MB ~ poucos GB. Produção (PostgreSQL): dezenas a centenas de GB por tenant. 1–10 TB exige outra arquitetura (object storage + ETL + particionamento).
Plano de ação — 6 frentes
Fase 0 — Estabilizar piloto (1–2 semanas)
Objetivo: parar de “perder dados” e ter ambiente confiável.

Ação	Entrega
0.1 Fixar banco único
Sempre smart_juno.db (local) ou PostgreSQL (prod); documentar qual fonte manda: upload do tenant vs Templates canônicos.
0.2 Confirmar persistência pós-upload

Fase 1 — Multi-usuário real (2–3 semanas)
Resposta direta: o JUNO já tem base multi-tenant, mas o piloto não está configurado para isso.

Ação	Entrega
1.1 Desligar JUNO_DEV_AUTH_BYPASS em staging/prod
Cada usuário com login próprio.
1.2 CRUD de usuários por tenant
Admin convida usuários, roles: owner, admin, member, viewer.
1.3 Sessões concorrentes
PostgreSQL + pool de conexões; testes com 10+ usuários simultâneos.
1.4 Isolamento auditável
Toda query filtrada por company_id; testes de vazamento entre tenants.
Meta: 50 usuários simultâneos por tenant em PostgreSQL (infra modesta).

Fase 3 — Depósito de dados + exclusão segura (2–3 semanas)
Problema que você descreveu: precisa depositar, consultar e apagar sob comando.

Ação	Entrega
3.1 Modelo DataDeposit
company_id, tipo, periodo, arquivo_origem, hash, rows, created_at, created_by, status.
3.2 Versionamento

3.3 Purge em 3 níveis
(a) período específico, (b) tipo ERP/financeiro, (c) tenant inteiro — sempre com token de confirmação.

Meta: nenhum upload “some” sem rastro; exclusão só com comando explícito do admin.
